## 一个待定项的解法：不必二选一

**问题**：加密后就不再是标准 VBAN，第三方 VBAN 软件（Voicemeeter 等）连不上。

**解法**：把加密做成**运行时开关**，而不是一次性架构决策。

| 模式 | 行为 |
| --- | --- |
| `secure`（默认） | AES-256-GCM，只有配过对的手机能进来 |
| `insecure` | 明文标准 VBAN，第三方软件照样能用 |

这样"要不要放弃第三方兼容"变成一个**每次可以选的开关**，而不是现在就要赌一把。
代码上是同一个 `ISecureEnvelope` 接口的两个实现（见批次 4），成本几乎为零。

### 批次 2：输出天花板 + 限幅（安全底线）

**目标**：`MixerEngine.Clamp()`（第 414 行）是硬削波，砍到的 1.0 就是满刻度＝耳机最大音量。
任何人往 6980 发满幅信号，耳机就是最大音量，**现在毫无防护**。加一道物理上限。

| 文件 | 改什么 |
| --- | --- |
| `src/AudioHub.Engine/OutputLimiter.cs`（新增） | 逐块算所需增益衰减，复用现有 `BlockCoefficient` 平滑套路 → **零新增延迟** |
| `src/AudioHub.Hosting/AudioHubOptions.cs` | 加 `OutputCeilingDb`（默认 −6 dB）+ 范围校验 |
| `src/AudioHub.Hosting/WindowsAudioHubHost.cs` | 接进管线，位置在 `Clamp` 之前 |
| `src/AudioHub.Cli/Program.cs` | 加 `--ceiling` |
| `tests/AudioHub.Tests/OutputLimiterTests.cs`（新增） | 见下 |

**必须钉死的验证（本批重点，全部客观、不需要耳朵）**
1. 灌 **+20 dB 增益的满幅恶意信号** → 输出峰值 ≤ 天花板
2. 灌 **−20 dB 正常音乐** → **逐样点完全不变**（透明性：平时不许动声音）
3. 天花板从高变低时相邻块增益差有上限（平滑，不产生新台阶）
4. 现有 101 个测试全绿，`--selftest` 仍 PASS

**不做**：不做攻击检测——限幅器不需要判断来源，这正是它的优点。

### 批次 4：密钥层 + 安全层（电脑端加密）

**方案（已定稿）**
- **密钥**：电脑首次运行生成 32 字节随机数 → Base32 约 26 个字符（≈130 bit 熵），
  显示在窗口与网页控制台，手机输一次，之后永久记住
- **派生**：`HKDF(PSK, 电脑 UUID)` → (AES-256 密钥, 4 字节会话盐)
- **加密**：**AES-256-GCM**；**薄信封**（明文只留 魔数+版本+类型+随机数+长度，其余全密文）
  → 垃圾包看魔数即丢、**现有到达间隔诊断不受影响**
- **随机数**：4 字节会话盐 ‖ 8 字节递增计数（同一密钥下绝不重复）
- 保留 `--insecure` 明文模式，用于排查与第三方兼容

| 文件 | 改什么 |
| --- | --- |
| `src/AudioHub.Core/Security/ISecureEnvelope.cs`（新增） | 接口：`Seal` / `Open` |
| `src/AudioHub.Core/Security/NullEnvelope.cs`（新增） | 明文直通（`--insecure` 与第三方兼容用） |
| `src/AudioHub.Core/Security/AesGcmEnvelope.cs`（新增） | AES-256-GCM 实现 |
| `src/AudioHub.Core/Security/HubKeyStore.cs`（新增） | PSK 生成 / Base32 编解码 / 持久化 / HKDF 派生 |
| `AudioHub.Sources.Vban` | UDP 收包后、现有解析器之前插入 `Open()` |
| `AudioHubOptions.cs` / `Program.cs` | `--secure auto|on|off`、`--show-key` |
| `tests/AudioHub.Tests/AesGcmEnvelopeTests.cs`（新增） | 见下 |
| `dist/probe-secure.bat`（新增） | 内置假手机：封 → 发 → 收 → 开 → 逐字节比对 → PASS/FAIL |

**必须钉死的验证**
1. 明文 → 封 → 开 → 明文，**逐字节相同**
2. 密文改任何一个字节 → **必须失败**，不得返回部分数据
3. **随机数重复 → 必须拒绝**（GCM 随机数重用会直接泄露密钥）
4. 用错密钥 → 失败，且不泄露任何明文
5. 外层头被篡改 → 失败（认证要覆盖头）
6. `probe-secure.bat` 自证；并测每包耗时，确认对延迟无实质影响

**本批电脑端可完全自证。**

**批次 5 与计划的两处出入（记下来，免得下次照旧计划对不上）：**

1. **计划里的 `android/discovery/` 模块，实际做成了 `android/protocol/`。**
   发现协议和加密信封放进了**同一个**模块，因为手机端用它们的时候总是一起用
   （先找到电脑，再拿密钥连上去），拆两个模块只是多一份 gradle 配置，没有收益。
   加密信封也没有放进计划里说的 `android/vban`——那里是纯 VBAN 编码，
   塞加密进去会让它依赖 `:protocol`（而后者还带着发现协议）。
   → 改成在 `VbanUdpSender` 上开一个 `PacketSealer` 函数式接口，`:vban` 保持零依赖。
2. **计划外的两件事，都是动手时才发现的**：
   - **`dist\show-key.bat` 原本不存在**，但手机界面的提示里让用户去跑它 ——
     不能让用户照着一条不存在的命令操作，所以补上了。
   - **`probe-vban` 原来只收明文**，于是"手机发来的加密包电脑能不能解开"这条
     在电脑上没有工具可查。给它加了 `--secure` 支持，另外做了 `probe-vban-secure.bat`。

**批次 5 最重要的产出是一个 bug，不是一个功能**（详见 CHANGELOG「批次 5」开头与
CONTINUE.md 第六节第 22、23 条）：`HubKeyStore.DeriveKey` 用了 Windows 布局的
`Guid.ToByteArray()`，和安卓侧的 RFC 4122 大端不一致，导致**两端派生出不同的 AES 密钥**，
而**两边都不报错**。批次 4 的 `probe-secure` 当时 PASS 是因为它自己封自己开，测不出来。
→ **凡是两端各自实现的东西，必须有一个第三方算出来的常数钉在中间。**

**批次 1 落地时与计划的两处出入**（记下来，免得下次照旧计划对不上）：

1. `run-tests.bat` 原本只打算"设好 dotnet PATH"。实际发现这台机器上 PATH 里的
   `C:\Program Files\dotnet\dotnet.exe` **只有运行时、没有 SDK**，照原样写会报
   "No .NET SDKs were found"。改成逐个候选跑 `dotnet --version` 探测，只接受带 SDK 的。
2. 托盘主窗口的收包状态**计划里没写**，是动手时发现 `MainWindow.xaml.cs` 里
   完全没有 VBAN 统计（grep 不到 `vban` / `accepted` / `Transport`）才补的。
   `IAudioHubHost` 因此新增 `TransportStats`。**托盘是多数人的实际入口，不能只有 CLI 会说话。**

**批次 2 落地时与计划的三处出入：**

1. **计划说 4 条钉死的断言，实际写了 11 条。** 因为限幅的安全属性很容易"静默丢失"——
   重排两级顺序、或把软拐点换回硬削波，代码看着还是个限幅器、别的测试全绿、
   而采样又能碰到满刻度了。所以每条断言对准一种丢失方式：单调性对应曲线回折、
   0.0005 步长扫描对应隐藏的拐点跳变、NaN 处理对应 NaN 绕过所有比较直达端点。
2. **`ceilingDb: 0` 的语义被迫改了一半。** 原本实现是"缩放系数设为 1"，
   结果软拐点还在生效 —— 说好的"无保护"没兑现，被一条旧测试抓出来（期望精确 1.0，
   实得 0.997）。**诊断开关必须是干净基线**，否则没法用它做对比。
   改成 0 dB 时整个 limiter 直通，并补了一条测试钉死这个语义。
3. **顺手修了参数校验，原计划里没有。** `--ceiling abc` 会被静默忽略（回退默认值却不告知，
   比报错更危险：让人以为设置生效了），越界值甩英文堆栈。
   现在所有数值参数统一前置校验，非数字/越界/缺值都给中文提示 + 退出码 2。
