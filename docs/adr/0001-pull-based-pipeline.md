# ADR 0001：管线采用拉取式，而非推送式

- 日期：2026-10-05
- 状态：已接受

## 背景

中枢要把多路音源混成一路再播出去。两种组织方式：

- 推送式：音源把数据推给混音器，混音器推给一个队列，输出设备从队列取。
- 拉取式：输出设备要数据时向混音器要，混音器向各通道要。

## 决定

采用拉取式。`IPcmSource.Read(Span<float>)` 由 `IAudioSink` 的渲染线程调用。

## 理由

推送式必须在混音器和设备之间放一个队列，队列需要自己的时序策略，于是多出一级缓冲和
第二个时钟。项目的核心矛盾就是蓝牙延迟，任何额外缓冲都与该目标直接冲突。

拉取式让设备时钟一路传导到通道，总延迟只由设备缓冲决定，也让"降低输出缓冲"成为唯一
需要调的旋钮。

## 代价

`MixerEngine.Read` 运行在设备实时线程上，因此：

- 不能分配内存（工作缓冲预分配，只在块长增长时扩容）；
- 不能阻塞，不能获取竞争激烈的锁；
- 所有重采样、闪避、求和都必须在一次调用内完成。

这个约束已经写进接口文档，后续所有实现都必须遵守。

## 备选方案

推送式 + 环形队列：实现更简单，但多一级缓冲，且需要自己决定队列水位，等于重新发明
一个设备时钟。否决。
