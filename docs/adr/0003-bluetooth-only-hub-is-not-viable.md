# ADR 0003：不让所有输入输出都走蓝牙

- 日期：2026-10-05
- 状态：已接受

## 背景

最初的想法是：以电脑为中枢，所有音源通过蓝牙进来，混好后再通过蓝牙发到耳机。
需要判断这条路在 Windows 上是否可行。

## 决定

不可行。蓝牙只用于最后一跳（中枢 → 耳机），音源侧走 Wi-Fi 或硬件接收器转线路输入。

## 理由

### 1. 带宽几乎没有余量

单个 BR/EDR 射频在音频场景下的实际可持续吞吐约 1.3 Mbps。三路 A2DP（两路接收 +
一路发射），按 SBC 328 kbps 加 L2CAP/ACL 封装与重传开销估算，需求约 1.26 Mbps，
余量约 3%。而蓝牙是半双工 TDD，收发分时占用同一射频，2.4 GHz 还要与 Wi-Fi、USB 3.0
争抢——一旦重传上来余量归零，表现是爆音、卡顿、断连。

### 2. 角色冲突

一个控制器理论上可同时做 A2DP Sink 和 Source，但 Windows 的 `BthA2dp` 驱动没有把
这个场景当作支持目标，实测经常互斥：连上接收端后输出设备消失，或反之。

### 3. 时钟域冲突

每条 A2DP 流有独立采样时钟，蓝牙设备之间没有共享时钟。多路混音必须做异步采样率转换，
否则会缓慢漂移并累积爆音。这也是实践中必须给每个蓝牙设备配独立 USB 适配器（独立 HCI
控制器、独立时钟域）的原因。

### 4. 缓冲三层串联

每条链路为抗抖动都有 100–250 ms 缓冲，两收一发串联就是 300–500 ms，且各路互相漂移。

### 5. 软件栈

Windows 原生不支持多 A2DP Sink 并发。Linux 的 BlueZ + bluez-alsa 才支持，能做到
"多 sink 接收 + 一路 source 发射"。

## 后果

- iPhone 接入（M5）走**硬件蓝牙接收器 → USB 声卡的线路输入**，完全绕开 Windows 蓝牙栈；
  或者走 AirPlay 接收器。不尝试让 Windows 直接当多设备 A2DP Sink。
- 安卓（M2）走 Wi-Fi 网传，延迟约 25 ms，明显优于蓝牙接收的 150–250 ms。
- 如果将来确实需要全蓝牙中枢，正确做法是换 Linux 中枢（树莓派 + BlueZ + bluez-alsa），
  届时只需替换 `Sources.*` 与 `Sinks.*`（见 ADR 0002）。
